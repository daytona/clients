# 0003. The `daytona` CLI

Status: implemented

## Context

Many Daytona tasks happen in a shell: signing in, creating a sandbox,
running a command in it, copying files, managing keys and projects. A CLI
serves those users better than a script against an SDK. It also has
different needs from the SDKs: it ships as a single binary, it has no import
surface, and it's installed next to an older 0.x CLI that existing users
still run.

## Decision

**Go, in this repository.** The CLI lives in [`cli/`](../../cli/) as its own
Go module with its own `go.mod`. It ships as a static binary, so users need
no runtime. It shares the version line of the SDKs (see
[0002](./0002-versioning-and-release-lines.md)): the publish workflow stamps
the version into the binary at build time.

**Wire types are generated from the contract.** [`cli/gen/`](../../cli/gen/)
holds Go types generated from [`contract/`](../../contract/) by
[`../../cli/hack/gen.sh`](../../cli/hack/gen.sh), the same contract the SDKs
build against. CI checks that the generated code is current, so a contract
change surfaces as a `go build` failure, not a runtime surprise.

**Its own scope, outside SDK parity.** The parity rule in
[0001](./0001-sdk-parity.md) binds the two SDKs to each other. It doesn't bind
the CLI. The CLI exposes what's useful from a shell: sandbox lifecycle,
`exec`, `ssh`, `cp`, processes and ports, images, snapshots, secrets,
registries, organizations, projects, members, keys, billing and audit. It
leaves out surfaces that only make sense from code, such as stateful
interpreter sessions and LSP. A feature can land in the SDKs without a CLI
command, and the CLI can add a command the SDKs don't need. The command
reference is in [`../../cli/README.md`](../../cli/README.md).

**Binaries and Homebrew.** [`../../cli/hack/build.sh`](../../cli/hack/build.sh)
builds six targets plus a `SHA256SUMS` file for each GitHub Release.
[`../../cli/install.sh`](../../cli/install.sh) and
[`../../cli/install.ps1`](../../cli/install.ps1) install from those releases
and verify the checksum. Homebrew formulae are maintained from
[`../../cli/hack/homebrew/`](../../cli/hack/homebrew/). While releases are
alpha-only, the CLI installs as the `daytona-alpha` formula.

**Naming across generations.** The 2.x CLI is `daytona`. Once 2.x is the
default release, the 0.x CLI ships from the `release/v0` line as a binary
named `daytona-v0` in a `daytona@0` formula, so both install side by side and
a user can keep scripts on the 0.x CLI while trying 2.x. Until then the 0.x
CLI keeps the `daytona` name and formula, and 2.x installs as
`daytona-alpha`.

**Config directories stay where they are.** Both CLIs honor
`$DAYTONA_CONFIG_DIR` first. The 2.x CLI then uses `$XDG_CONFIG_HOME/daytona`,
falling back to `~/.config/daytona`
([`../../cli/internal/config/config.go`](../../cli/internal/config/config.go)).
The 0.x CLI keeps its own location under the operating system's user config
directory. Where the two directories coincide, the files don't: the 0.x CLI
writes `config.json`, and the 2.x CLI writes `config.yaml` and
`credentials.yaml`. Neither CLI reads or deletes the other's files.

## Alternatives

**A CLI built on one of the SDKs.** A Python or Node CLI needs a runtime on
the user's machine and starts slower. A Go binary has neither cost, and the
generated wire types keep it on the same contract as the SDKs.

**Holding the CLI to SDK parity.** Mirroring every SDK method as a command
produces a large CLI full of commands nobody runs from a shell, and forces
SDK-only features to wait for CLI design. A separate scope lets each surface
fit its users.

**A new binary name for 2.x, keeping `daytona` for 0.x.** Tools such as `gh`,
`kubectl` and the AWS CLI keep their name across major versions and offer
versioned formulae for the old one. Following that norm means new users type
`daytona`, and `2.0.0` sorts above every `0.x` so the formula moves forward
without a rename.

**A new config directory for 2.x.** Moving configuration would strand
existing setups for no gain, since the file names already keep the two CLIs
apart.

## Consequences

- Users install the 2.x CLI as `daytona` and keep the 0.x CLI available as
  `daytona-v0` through `daytona@0`. Scripts that call `daytona` get 2.x once
  they upgrade the formula.
- Users who set `DAYTONA_API_URL` for the 0.x CLI should unset it: the 2.x CLI
  reads the same variable and would send requests to that host.
- Contributors don't need to add a CLI command for every SDK feature, and SDK
  pull requests don't need CLI changes.
- A contract change can break the CLI build. Regenerate with
  `cli/hack/gen.sh` and adapt the commands.
- The CLI is licensed AGPL-3.0 ([`../../cli/LICENSE`](../../cli/LICENSE));
  the SDKs are Apache-2.0.
- Renaming the binary, the formulae or the config files is now a breaking
  change for installed users.
- Scripts depend on the CLI the way programs depend on the SDKs. From
  `2.0.0` on, its stability contract (command paths, flags, JSON output
  fields, exit codes, environment variables, configuration files and
  `--file` request bodies, but not table layout, help text or progress
  output) is in [`../VERSIONING.md`](../VERSIONING.md), "The CLI".
